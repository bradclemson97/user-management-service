## 1. Overview

This application is a role-based access control (RBAC) user management platform built across four services:

| Service | Technology | Responsibility |
|---|---|---|
| `user-management-ui` | Node.js, Express, TypeScript | Server-side rendered GOV.UK interface |
| `user-management-service` (UMS) | Spring Boot 3, Java 17 | User identity, profile, and account lifecycle |
| `access-control-manager` (ACM) | Spring Boot 3, Java 17 | Roles, permissions, and capability enforcement |
| `keycloak-manager` (KM) | Spring Boot 3, Java 17 | Keycloak admin API proxy and protocol mapper setup |

All four services share a single PostgreSQL instance split across two schemas (`user_management` and `access_control`) and a single Keycloak realm (`system`). Authentication is OIDC-based; authorisation is enforced by capability claims embedded directly in signed JWTs.

## 2. Features

### 2.1 User Creation and Role / Permission Assignment

#### User Creation

Creating a new user is orchestrated by UMS as a distributed transaction across three systems — the local database, Keycloak (via KM), and ACM — using a Saga compensation pattern.

**Step-by-step flow:**

1. A user with the `Create users` capability submits the create-user form in the UI.
2. The UI sends `POST /v1/user` to UMS with the new user's details and a pre-assigned `systemUserId` (UUID).
3. UMS persists the `users` and `user_details` records to its database within a transaction.
4. UMS calls KM's `POST /v1/user`. KM creates the Keycloak account with the `systemUserId` stored as a user attribute and returns a generated temporary passphrase.
5. UMS calls ACM's `POST /v1/user` to initialise the user's permission record in the `access_control` schema.
6. If the ACM call fails, UMS calls KM's `DELETE /v1/user/rollback/{email}` to remove the Keycloak account, ensuring the identity provider stays in sync with the application state. The transaction is then rolled back.
7. On success, the temporary passphrase is returned to the UI and displayed once. The user must set a permanent password on first login.

The passphrase is generated by KM as a hyphen-separated sequence of four English words (minimum 17 characters total, minimum 4 characters per word, no duplicates).

#### Role and Permission Assignment

The RBAC model is built on two role types:

| Type | Description |
|---|---|
| `PERMISSION` | A named role that can be assigned directly to a user (e.g. "User Administration") |
| `CAPABILITY` | A granular action string checked at the API level (e.g. "Create users") |

PERMISSION roles inherit CAPABILITY roles through the `role_inheritances` table. The three system PERMISSION roles and their inherited capabilities are:

| Permission Role | Inherited Capabilities |
|---|---|
| **User Core Access** | Sign in, Sign out, Search and View users, Manage own password, Update own user profile |
| **Customer Maintenance** | Manage customers, Create customer, Update customer |
| **User Administration** | Create users, Manage permissions given to a user, Manage users account |

A fourth inheritance type — `ASSIGNMENT` — controls who can assign roles. `User Administration` holders may assign any PERMISSION role to other users.

**Role assignment flow:**

1. An authorised user (must hold `Manage permissions given to a user`) navigates to a user's roles page in the UI.
2. They select the desired PERMISSION roles and submit.
3. The UI posts to `POST /v1/userRoles/{systemUserId}/roles` on ACM.
4. ACM verifies that the assigner holds the `ASSIGNMENT` relationship to every role being added or removed.
5. The new role set is persisted to `access_control.user_roles`, replacing the prior set. Removed roles move to `user_roles_history` via the versioning trigger.
6. ACM resolves the user's full capability set (traversing the inheritance hierarchy) and their direct PERMISSION roles, then calls `PUT /v1/user/{systemUserId}/permissions` on KM.
7. KM writes `capabilities` and `systemRoles` as Keycloak user attributes. These are embedded in the next JWT issued to that user.

The UI presents a **two-step confirmation** before applying role changes: the first form captures the selection; a second confirmation page shows the before-and-after diff before the change is committed.

### 2.2 Account Activity Indicator and Inactivity Scheduler

Every user record carries an `active_ind` field (`YES`/`NO`) and a `last_login_date` timestamp. These are set by two mechanisms:

**Login tracking:** When a user authenticates through the UI, the OIDC callback calls `PUT /v1/user/{systemUserId}/recordLogin` on UMS, which stamps `last_login_date = now()` on the user record.

**Inactivity scheduler:** `UserInactivityScheduler` runs daily at midnight (cron: `0 0 0 * * *`). It queries for all users where `active_ind = YES` and `last_login_date < now() - 60 days`. Any matching users are set to `active_ind = NO`. Users who have never logged in are measured from their account creation date instead.

```
Threshold: 60 days of no login activity
Schedule:  Daily at 00:00 UTC
Action:    Sets active_ind = NO (does not lock or delete the account)
```

The `active_ind` status is displayed on the user list and user detail pages in the UI, giving administrators an at-a-glance view of which accounts are dormant.

### 2.3 Password Reset

An administrator with the `Manage users account` capability can reset a user's password from the user detail page in the UI.

**Flow:**

1. The administrator clicks **Reset password** on the user detail page.
2. The UI sends a request to UMS, which calls `PUT /v1/user/{email}/password` on KM.
3. KM generates a new passphrase (same word-list algorithm as initial creation) and calls the Keycloak Admin API to set it as a temporary credential.
4. The new passphrase is returned through UMS to the UI and displayed once.
5. Keycloak marks the credential as temporary — the user must change it on next login.

The passphrase is never stored in any database. It is only held in memory for the duration of the request/response cycle.

### 2.4 Account Locking and Unlocking

An account can become locked in two ways: automatically by a scheduled job that detects Keycloak brute-force events, or manually by an administrator.

#### Automatic Lock Sync

`UserLockSyncScheduler` runs hourly (cron: `0 0 * * * *`). For each active user it calls KM's `GET /v1/user/{email}/lockoutStatus`, which queries the Keycloak Admin API's attack-detection endpoint. If Keycloak reports the user as locked **or** their failed attempt count reaches the threshold (5), UMS sets `locked_user_ind = YES` and records the current `failed_login_attempts` count.

```
Lock threshold:  5 failed login attempts in Keycloak
Schedule:        Hourly
Scope:           Active users only (active_ind = YES)
```

ACM maintains a mirrored `locked` field on its own `access_control.users` table and is notified of lock/unlock events via `POST /v1/user/{systemUserId}/lock` and `POST /v1/user/{systemUserId}/unlock`, so capability checks reflect the account state without a cross-schema join.

#### Manual Unlock

An administrator with the `Manage users account` capability can unlock an account via the user detail page in the UI.

**Unlock flow:**

1. UMS sets `locked_user_ind = NO` and resets `failed_login_attempts = 0` in the `user_management` database.
2. UMS calls KM's `PUT /v1/user/{email}/unlock`, which clears the Keycloak brute-force state and re-enables the account.
3. UMS notifies ACM's unlock endpoint to sync the `locked` flag in the `access_control` schema.

#### Login Guard

When a user successfully authenticates via Keycloak, the UI's OIDC callback calls UMS to retrieve the current user record. If `locked = true` is returned, the session is destroyed immediately and the user is redirected to the `/auth/account-locked` page rather than being admitted to the application.

### 2.5 Audit Trail and Observability

#### Temporal History Tables

Every state change to `users`, `user_details`, and `user_roles` is automatically recorded using PostgreSQL temporal versioning. Each live table has a corresponding `_history` table (e.g. `users_history`, `user_roles_history`) and a `sys_period tstzrange` column tracking the validity window of each row.

A `versioning()` trigger fires `BEFORE UPDATE OR DELETE` on each table, copying the current row to the history table with `upper(sys_period)` set to `now()` before the change is applied. Inserts are not recorded in history — only changes and deletions.

The history page at `/users/:id/history` in the UI presents two tables:

- **Account changes** — every update to `active_ind`, `locked_user_ind`, or `failed_login_attempts`, with the change timestamp, who made it, and when it was superseded.
- **Role assignment history** — every role grant and revocation, showing the role name, type, assigner, assignment date, and removal date (or "Active" if currently held). The role history query uses a `UNION ALL` to combine `user_roles_history` (past assignments, `valid_to` set) with the current `user_roles` records (`valid_to = NULL`), ensuring newly assigned roles appear immediately.

Both history tables join across schemas to `user_management.user_details` to resolve the modifier's name rather than displaying a raw UUID.

#### Structured Logging with MDC

`RequestMdcFilter` (a `OncePerRequestFilter` in UMS) runs on every inbound HTTP request and populates the SLF4J Mapped Diagnostic Context with two values:

| MDC Key | Source |
|---|---|
| `correlationId` | `X-Correlation-Id` request header, or a freshly generated UUID if absent |
| `systemUserId` | Decoded from the Bearer JWT payload (Base64 URL-decode of the middle segment, string scan for `"systemUserId":"`) |

The `correlationId` is also echoed back as a response header, enabling end-to-end request tracing across service boundaries when forwarded between UMS, ACM, and KM.

The Logback pattern includes both values on every line:

```
[cid=<correlationId>] [uid=<systemUserId>] - <message>
```

## 3. Architecture

### 3.1 Data Model and Entity Relationships

The application uses two PostgreSQL schemas on the same database instance.

#### `user_management` schema

```
users
├── usr_id          BIGSERIAL PK
├── system_user_id  UUID  UNIQUE  (shared identity key across all services)
├── locked_user_ind VARCHAR(10)   (YES / NO / NA)
├── active_ind      VARCHAR(10)   (YES / NO)
├── last_login_date TIMESTAMPTZ
├── failed_login_attempts INT
├── sys_period      TSTZRANGE     (temporal versioning)
└── audit fields    (created_by, created_date, modified_by, modified_date)

user_details                           (one-to-many on usr_id — supports historical name records)
├── udl_id          BIGSERIAL PK
├── user_detail_id  UUID UNIQUE
├── usr_id          FK → users.usr_id
├── title / first_name / middle_name / last_name
├── primary_email   VARCHAR NOT NULL
├── known_from_date TIMESTAMPTZ     (start of this detail record's validity)
├── known_to_date   TIMESTAMPTZ     (null = currently active record)
└── audit fields

users_history       (mirror of users — rows moved here on UPDATE/DELETE)
user_details_history
```

**User details versioning:** When a user's profile is updated, the existing `user_details` record is closed (`known_to_date = now()`) and a new record is inserted. The current record is always the one where `known_to_date IS NULL`. This preserves the full name history without ever overwriting data.

#### `access_control` schema

```
roles
├── roe_id          BIGSERIAL PK
├── role_name       VARCHAR(50) UNIQUE
├── role_type_code  VARCHAR(10)   (PERMISSION or CAPABILITY)
└── audit fields

role_inheritances                      (defines the capability graph)
├── rie_id          BIGSERIAL PK
├── roe_id          FK → roles (the parent role)
├── inherits_roe_id FK → roles (the child role)
└── inheritance_type_code  (INHERIT or ASSIGNMENT)

users
├── usr_id          BIGSERIAL PK
├── system_user_id  UUID UNIQUE
├── locked          BOOLEAN
└── audit fields

user_roles                             (currently active assignments)
├── ure_id          BIGSERIAL PK
├── usr_id          FK → access_control.users
├── roe_id          FK → roles
├── sys_period      TSTZRANGE
└── audit fields

user_roles_history  (mirror of user_roles — rows moved here on UPDATE/DELETE)
```

#### Cross-schema relationship

Both schemas share identity via `system_user_id` (UUID). There is no foreign key across schemas — the UUID acts as the correlation key. ACM history queries join `access_control.user_roles_history` with `user_management.user_details` for display names, which is valid because both schemas live on the same PostgreSQL instance.

### 3.2 User Creation and Role Assignment Across Microservices

#### User Creation — Saga Pattern

```
UI (POST /users/create)
  │
  └─► UMS  POST /v1/user
         │
         ├─1─► DB: INSERT users + user_details  ─── @Transactional
         │
         ├─2─► KM  POST /v1/user
         │          └─► Keycloak Admin API: create user
         │               attributes: { systemUserId: "<uuid>" }
         │               return: temporary passphrase
         │
         ├─3─► ACM  POST /v1/user
         │          └─► DB: INSERT access_control.users
         │
         │     [if ACM fails]
         │          └─► KM  DELETE /v1/user/rollback/{email}  ← compensation
         │               └─► Keycloak Admin API: delete user
         │
         └─► return: { systemUserId, password }
```

UMS owns the transaction. Keycloak and ACM are called in sequence after the local commit. The Keycloak creation is not within the Spring transaction — if ACM fails after Keycloak succeeds, the compensation call to KM rolls back the Keycloak record so all three systems remain consistent.

#### Role Assignment — Sync to Keycloak

```
UI (POST /users/:id/roles/confirm)
  │
  └─► ACM  POST /v1/userRoles/{systemUserId}/roles
         │
         ├─1─► Validate assigner has ASSIGNMENT rights for all role changes
         │
         ├─2─► DB: UPDATE user_roles (removed roles → user_roles_history via trigger)
         │
         └─3─► KmClient  PUT /v1/user/{systemUserId}/permissions
                    │
                    └─► KM resolves:
                         capabilities = inherited CAPABILITY-type roles (full traversal)
                         systemRoles  = direct PERMISSION-type roles
                    │
                    └─► Keycloak Admin API: update user attributes
                         user.attributes.capabilities = [...]
                         user.attributes.systemRoles  = [...]
```

If the KM call fails (non-fatal), ACM logs a warning, the role save succeeds, and JWT claims will be stale until the next successful sync. The existing fallback path in the security library ensures services continue to function.

### 3.3 User Login and Authentication

The UI uses the OIDC Authorization Code flow with PKCE, handled by the `openid-client` library.

```
Browser                  UI (Express)              Keycloak             UMS / ACM
   │                         │                        │                     │
   │── GET /auth/login ──────►│                        │                     │
   │                         │── redirect ────────────►│                     │
   │                         │   (state, nonce,        │                     │
   │                         │    code_challenge)       │                     │
   │◄────── 302 to Keycloak ─│                        │                     │
   │                         │                        │                     │
   │── login ───────────────────────────────────────►│                     │
   │◄── code + state ──────────────────────────────────│                     │
   │                         │                        │                     │
   │── GET /auth/callback ───►│                        │                     │
   │                         │── token exchange ──────►│                     │
   │                         │◄── access_token ────────│                     │
   │                         │    id_token             │                     │
   │                         │    refresh_token         │                     │
   │                         │                        │                     │
   │                         │── decode JWT payload    │                     │
   │                         │   read systemUserId     │                     │
   │                         │   read systemRoles claim│                     │
   │                         │                        │                     │
   │                         │── GET /v1/user/current ─────────────────────►│ (UMS)
   │                         │◄── { locked: false, ... } ───────────────────│
   │                         │                        │                     │
   │                         │   if locked → destroy session → /account-locked
   │                         │                        │                     │
   │                         │── PUT /v1/user/{id}/recordLogin ────────────►│ (UMS)
   │                         │   (stamps last_login_date = now())           │
   │                         │                        │                     │
   │                         │── req.session.regenerate()   (session fixation)
   │                         │   store: accessToken, currentUser,           │
   │                         │          currentUserRoles                    │
   │                         │                        │                     │
   │◄── 302 / ──────────────│                        │                     │
```

**`systemRoles` resolution:** The callback reads `jwt.systemRoles` from the decoded access token payload. If the claim is present and non-empty (i.e. JWT embedding is active), it is used directly and no ACM call is made. If the claim is absent (first login before KM has synced permissions, or tokens predating the protocol mapper), it falls back to calling ACM's `GET /v1/userRoles/{systemUserId}/roles`.

**Token refresh:** A middleware in `app.ts` proactively refreshes the access token when it is within 60 seconds of expiry, using the stored refresh token. Updated tokens are written back to the session. This happens transparently on every request.

### 3.4 JWT Permissions Embedding

This is the mechanism that eliminates the per-request ACM capability lookup for all downstream services.

#### Why it exists

Without JWT embedding, every API request to UMS or ACM triggers a synchronous call from the `security-library`'s `AccessControlAuthenticationConverter` to ACM's `/capabilities` endpoint to resolve what the caller is allowed to do. This creates a hard runtime dependency: if ACM is momentarily unavailable, all authenticated API calls fail. Embedding permissions in the signed JWT breaks this dependency.

#### How it works — end to end

```
1. KM STARTUP
   RealmSetupService (@PostConstruct)
   └─► Keycloak Admin API: create protocol mappers (idempotent)
        ┌─────────────────────────────────────────────────────────┐
        │ Mapper: capabilities                                    │
        │   type: oidc-usermodel-attribute-mapper                 │
        │   user.attribute → capabilities                         │
        │   claim.name     → capabilities                         │
        │   multivalued    → true                                 │
        │   access.token   → true                                 │
        └─────────────────────────────────────────────────────────┘
        (identical mapper created for systemRoles)

2. ROLE CHANGE
   ACM UserRoleServiceImpl.syncPermissionsToKm()
   └─► KM  PUT /v1/user/{systemUserId}/permissions
        └─► Keycloak Admin API: update user attributes
             user.attributes.capabilities = ["Create users", "Search and View users", ...]
             user.attributes.systemRoles  = ["User Administration"]

3. NEXT TOKEN ISSUANCE / REFRESH
   └─► Keycloak embeds attributes as signed JWT claims:
        {
          "systemUserId": "...",
          "capabilities": ["Create users", "Search and View users"],
          "systemRoles":  ["User Administration"]
        }

4. INBOUND API REQUEST
   Spring Security validates JWT (signature + expiry)
   └─► AccessControlAuthenticationConverter
        if jwt.capabilities present and non-empty:
          → load authorities directly from claim (no HTTP call)
        else:
          → GET /v1/user/{systemUserId}/capabilities on ACM (fallback)
   └─► SecurityContext populated with CapabilityGrantedAuthority objects

5. AUTHORISATION CHECK
   @RequiresCapability("Create users")
   └─► CapabilityAuthorizationManager checks SecurityContext
        match → proceed
        no match → HTTP 403
```

#### Staleness window

Capabilities are embedded at token issuance. A role change takes effect within one Keycloak access token TTL (default 5 minutes) — the next token issued after the role change carries the updated claims. This is standard practice for token-based permissions and represents an acceptable operational trade-off for the elimination of per-request ACM calls.

#### Fallback path

`AccessControlAuthenticationConverter` always falls back to the ACM HTTP call if the `capabilities` claim is absent or empty. This handles:
- Tokens issued before the protocol mappers were registered
- Tokens issued before a user's first role assignment
- Environments where KM is temporarily unavailable during a deploy

### 3.5 Security

#### Session Management (UI)

| Property | Value |
|---|---|
| Storage | Server-side (`express-session`). Browser holds only a session cookie. |
| Cookie flags | `httpOnly: true`, `secure: true` (production), `sameSite` default |
| Max age | 8 hours |
| Session fixation | `req.session.regenerate()` is called in the OIDC callback after successful token exchange. All session data is captured before the call and re-written to the new session ID inside the callback — old session ID is invalidated. |
| Token storage | Access, ID, and refresh tokens are stored in the server-side session only. They are never sent to the browser. |

#### CSRF Protection (UI)

All state-changing HTTP requests (POST, PUT, PATCH, DELETE) are protected by a synchronizer token pattern:

1. On first session access, a 32-byte cryptographically random token (`crypto.randomBytes(32).toString('hex')`) is generated and stored in `req.session.csrfToken`.
2. The token is injected into `res.locals.csrfToken` on every response via middleware.
3. All HTML forms include a hidden `_csrf` field populated from `res.locals.csrfToken`.
4. The CSRF middleware validates that the submitted `_csrf` value matches the session token. Mismatch returns HTTP 403.

#### HTTP Security Headers (UI — Helmet)

| Header | Policy |
|---|---|
| `Content-Security-Policy` | `default-src 'self'`, `script-src 'self'` (no `unsafe-inline` — GOV.UK Frontend initialisation extracted to `public/js/init.js`) |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains; preload` |
| `X-Frame-Options` | `SAMEORIGIN` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| `Permissions-Policy` | defaults |

#### Rate Limiting (UI)

The OIDC login initiation endpoint (`/auth/login`) is rate-limited to **20 requests per 15 minutes** per IP address using `express-rate-limit`. This limits the impact of automated login-page probing without affecting normal users.

#### Spring Security (UMS / ACM / KM)

All three Spring services are stateless JWT resource servers. The security configuration follows the same pattern:

- All requests require a valid Bearer JWT signed by the configured Keycloak realm issuer URI (`KEYCLOAK_ISSUER_URI`).
- Public paths exempt from authentication: `/actuator/health`, `/v1/docs`, `/v1/docs/**`, `/v1/api-docs`, `/v1/api-docs/**`, `/swagger-ui/**`.
- CSRF is disabled (stateless; no cookies).
- Session creation policy: `STATELESS`.

ACM uses two ordered `SecurityFilterChain` beans to break a circular dependency: the `GET /v1/user/*/capabilities` endpoint uses a plain JWT chain (no capability lookup), while all other endpoints use the `AccessControlAuthenticationConverter` that would otherwise call that same endpoint to authenticate the caller.

#### Method-Level Authorisation

UMS and ACM endpoints are annotated with `@RequiresCapability`, which is enforced by `CapabilityAuthorizationManager` reading `CapabilityGrantedAuthority` objects from the `SecurityContext`. Capability strings match the `role_name` values of `CAPABILITY`-type roles exactly (space-separated, title case — e.g. `"Create users"`, `"Manage users account"`).

### 3.6 UI — GOV.UK Design System and Permission-Driven Rendering

The UI is built with **GOV.UK Frontend v6.4.0** and rendered server-side using **Nunjucks** templates. All pages conform to GOV.UK Design System standards: typography, spacing, component patterns, and the GOV.UK logotype.

#### Middleware stack (in order)

| Middleware | Purpose |
|---|---|
| `helmet` | Security headers |
| `express-session` | Session store |
| Token refresh | Proactive access-token renewal |
| `csrfMiddleware` | Token generation and validation |
| Flash message | Move `req.session.flashMessage` → `res.locals` for one-time display |
| Rate limiter | Applied to `/auth/login` only |
| `requireAuth` | Redirects unauthenticated requests to `/auth/login` |
| `requireRole` | Checks `req.session.currentUserRoles` against required permission roles |

#### Permission-driven rendering

Route-level access control uses the `requireRole` middleware, which checks that `req.session.currentUserRoles` includes the specified PERMISSION role before the route handler runs. Requests that fail this check receive a rendered GOV.UK-styled `errors/403.njk` page.

```typescript
// Example — only "User Administration" role holders can access role management
router.get('/:id/roles', requireRole('User Administration'), ...)
```

Within templates, UI elements (such as action buttons for locking, unlocking, editing, or resetting passwords) are rendered conditionally by inspecting `currentUserRoles` passed via `res.locals`:

```nunjucks
{% if "User Administration" in currentUserRoles %}
  {{ govukButton({ text: "Reset password", ... }) }}
{% endif %}
```

This means the same user detail page adapts its available actions based on the viewer's permissions — a read-only user sees the profile but none of the management controls.

#### GOV.UK components in use

| Component | Used for |
|---|---|
| `govukTable` | User list, audit history, role assignment |
| `govukButton` | Actions (create, save, reset, lock/unlock) |
| `govukInput` / `govukSelect` | Create user form, search, profile edit |
| `govukBreadcrumbs` | Navigation context on all pages |
| `govukNotificationBanner` | Success feedback after state-changing actions (flash messages) |
| `govukErrorSummary` | Form validation error display |
| `govukTag` | Active / inactive status indicator on user list |

#### Error pages

Dedicated GOV.UK-styled error pages are served for:

| Condition | Page | HTTP Status |
|---|---|---|
| CSRF token mismatch | `errors/403.njk` | 403 |
| Insufficient role | `errors/403.njk` | 403 |
| No route matched | `errors/404.njk` | 404 |
| Unhandled server error | `errors/500.njk` | 500 |

#### Flash messages

Success feedback after actions (user updated, roles saved, account unlocked, password reset) is stored in `req.session.flashMessage` before each redirect. A middleware at the top of the stack reads the message once, places it in `res.locals.flashMessage`, and clears the session entry. The base Nunjucks layout renders a `govukNotificationBanner` (success type) if `flashMessage` is set.
